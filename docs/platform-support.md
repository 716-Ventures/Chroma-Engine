# Platform Support

Chroma Engine separates portable container/session code, software codecs, and platform hardware adapters. A successful build does not imply that every transcode stage is executable on that host.

| Target | Build and core tests | Software video codecs | AAC-LC software encode | Hardware video encode/decode | Full native HLS transcode |
| --- | --- | --- | --- | --- | --- |
| macOS x86-64 / ARM64 | Supported | H.264 decode/encode; HEVC Main/Main10 decode; AV1 decode via dav1d | Safe Rust fallback; AudioToolbox preferred | VideoToolbox executable | H.264/HEVC/AV1 with copy-compatible audio or TrueHD/DTS-to-AAC |
| Windows x86-64 / ARM64 | Supported | H.264 decode/encode; HEVC Main/Main10 decode; AV1 decode via dav1d | Safe Rust scalar backend | Retained H.264/HEVC Main encoding selects hardware NVENC, hardware Intel Quick Sync, or native Media Foundation after a real encode smoke; Media Foundation/D3D11 H.264 hardware decode is executable after a real round-trip smoke; hardware HEVC decode remains pending | H.264/HEVC/AV1 with copy-compatible audio or TrueHD/DTS-to-AAC |

The portable H.264 codec is source-built into the Rust binary dependency graph. Building from source therefore requires a working C/C++ toolchain; deployed release binaries do not need an external OpenH264 installation. OpenH264 is BSD-2-Clause licensed. Distributors remain responsible for evaluating codec patent and royalty obligations for their products and territories.

Portable HEVC Main/Main10 decoding is implemented in safe Rust and converts 8-bit or 10-bit YUV420 frames into the engine's BGRA boundary. It has no system-library or native-toolchain dependency. HEVC can carry additional profiles and chroma layouts outside this backend's declared scope; those fail explicitly instead of silently producing incompatible output.

Portable AV1 decoding uses the safe `dav1d-rs` API over VideoLAN's native libdav1d and accepts 8-, 10-, and 12-bit monochrome, 4:2:0, 4:2:2, and 4:4:4 output at the engine's BGRA boundary. Source builds require libdav1d 1.3 or newer plus `pkg-config`: Homebrew `dav1d` on macOS, vcpkg `dav1d` on Windows, or the distribution's dav1d development package on Linux/NAS. CI installs this dependency on every supported hosted architecture. Auditable release jobs copy the matching library beside the executable and rewrite macOS/Linux loader paths to resolve it from the bundle, so packaged releases do not require a separate system installation. NAS distributors can use the Linux bundle when its libc baseline matches the appliance, or rebuild it against the oldest supported appliance SDK.

The portable AAC-LC, AC-3, and E-AC-3 encoders are built from safe Rust, so they do not require a system codec library or native build toolchain. They emit raw access units plus the decoder configuration needed by the existing fMP4 muxer for one to six channels. The safe Rust TrueHD decoder selects the format-defined six-channel presentation (or the closest smaller presentation). The pinned Rust `oxideav-dts` decoder retains DTS Core synthesis state, accepts standard big-endian core frames carried in DTS/DTS-HD packets, and emits up to six canonical interleaved PCM channels. Both decoders can feed the portable audio encoders without a system codec dependency.

CI runs the complete check, Clippy, test, documentation, and release-build gates on hosted macOS, Ubuntu, and Windows x86-64-class runners. Additional native Ubuntu ARM64 and Windows ARM64 jobs compile all targets, exercise the CPU codec, and build the release binary. NAS vendors with custom libc versions or older kernels should validate the release binary on the oldest supported appliance image before publishing it.

Hardware capability states stay deliberately conservative: `modeled` and `detected` backends cannot be selected. Only executable or verified implementations may enter a runtime plan.

Windows probing initializes COM and Media Foundation, enumerates hardware-only H.264 and HEVC decoder and encoder transforms, activates a matching transform, releases every activation object, and balances platform shutdown. Retained H.264/HEVC Main encode sessions convert the shared BGRA boundary to NV12, try NVENC and Quick Sync before the native Media Foundation path, and advertise only a backend that completes a real encoded-frame smoke. Retained H.264 decode submits compressed access units to a hardware-only Media Foundation transform on a Chroma-owned D3D11 device, copies returned NV12 textures through a same-device staging resource, respects mapped row pitch, converts to BGRA, and restores source timing. D3D11VA becomes executable only after a CPU-encoded probe frame completes that full path. Successfully activated HEVC transforms still report `opened`, not `available`, until an equivalent hardware output path is wired.

Linux VA-API probing loads `libva.so.2` and `libva-drm.so.2` at runtime, opens each DRM render node, checks H.264/HEVC profiles for the VLD decode entrypoint, and creates a small codec config, surface, and decode context. It also synchronizes each probe surface, derives its NV12 or P010 image, validates plane geometry, and maps the image buffer for CPU access when the driver supports direct derivation. The `linux-vaapi` build feature additionally submits H.264 and HEVC parameter sets and slices through retained stateless decoders into page-aligned NV12/P010 user-pointer surfaces. Build hosts need Clang and libva headers for generated bindings; shipped binaries retain runtime loading and do not link against libva. A missing runtime, inaccessible device, unsupported profile, allocation failure, or mapping limitation leaves the portable CPU path intact and reports a diagnostic through `decoder-probe`.

On Linux, Quick Sync uses Intel's standard VA-API exposure instead of adding a link-time oneVPL dispatcher dependency. Chroma scans render nodes for an Intel/iHD/i965 vendor, binds retained H.264 and HEVC sessions to that exact display, and requires real encode or decode capability probes before advertising `qsv`. Generic or non-Intel VA-API devices remain labeled `vaapi`; systems without the Intel driver keep the same portable fallback.

The decoded-surface boundary accepts independently padded NV12 or P010 Y and UV planes and copies them into tightly packed BGRA with checked dimensions and plane bounds. H.264 and HEVC Main/Main10 use that path today. The H.264 and HEVC Main encoders perform the inverse checked BGRA-to-NV12 upload and convert hardware Annex-B output to length-prefixed samples plus avcC/hvcC for the existing fMP4 muxer.
